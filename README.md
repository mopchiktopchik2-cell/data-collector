Имитатор устройств сбора данных и очередь сообщений

Учебный проект по Python. Имитирует несколько датчиков, которые шлют данные
в очередь, а обработчик их валидирует и сохраняет в SQLite.

Как запустить

Открываем терминал в папке проекта и пишем:

    venv\Scripts\activate          (Windows)
    source venv/bin/activate       (Linux/Mac)

    python main.py

Всё. Программа запустится и через 30 секунд сама завершится.
Если хочешь остановить раньше - жми Ctrl+C, она закроется нормально.

Что происходит при запуске

1. Создаётся база `data_collector.db` (если её ещё нет) и таблица `measurements`.
2. Запускается 8 виртуальных устройств (по 2 на каждый тип датчика).
3. Каждое устройство периодически генерирует показание и кладёт его в очередь.
4. Обработчик забирает сообщения из очереди, проверяет их и сохраняет в БД.
5. Каждые 5 секунд в консоль летит статистика.
6. По истечении RUN_TIME всё аккуратно останавливается, БД закрывается,
   выводится финальная статистика.

Датчики

Всего 4 типа, каждый наследуется от `BaseDevice`:

- temperature - температура, от -30 до 45 °C
- humidity    - влажность, от 0 до 100 %
- pressure    - давление, от 950 до 1050 hPa
- power       - мощность, от 0 до 5000 W

У каждого устройства свой `device_id` вида `temperature_00`, `power_01` и так далее.

Очередь

Обычная `asyncio.Queue` с ограничением по размеру. Если очередь заполнена,
новое сообщение отбрасывается, счётчик `dropped` увеличивается. Это видно
в логах и в статистике.

Обработка

Обработчик берёт сообщение из очереди, проверяет:
- что это вообще Message
- что device_id и device_type непустые
- что value - число, не NaN и не бесконечность
- что timestamp парсится как ISO

Если что-то не так - сообщение не сохраняется, счётчик ошибок растёт,
обработчик идёт дальше. Ничего не падает.

Хранилище

SQLite через стандартный `sqlite3`. Работает в отдельном потоке через
`asyncio.to_thread`, чтобы не блокировать event loop.

Таблица `measurements`:
- id
- device_id
- device_type
- timestamp
- value
- unit
- processed_at

Посмотреть, что записалось, можно так:

    python -c "import sqlite3; c=sqlite3.connect('data_collector.db'); [print(r) for r in c.execute('SELECT * FROM measurements LIMIT 10')]"

Или через DB Browser for SQLite - там просто открыть файл `data_collector.db`.

Статистика

Каждые N секунд выводится:
- сколько всего получено сообщений
- сколько успешно обработано
- сколько ошибок
- текущий размер очереди
- сколько сообщений отброшено (если очередь переполнялась)
- количество сообщений по каждому устройству
- среднее, минимум и максимум по каждому типу датчика

Настройки

Всё в `config.py`:

- NUM_DEVICES - сколько устройств запускать
- QUEUE_MAXSIZE - максимальный размер очереди
- STATS_INTERVAL - как часто выводить статистику (в секундах)
- RUN_TIME - сколько работать; None = до Ctrl+C
- DB_PATH - путь к файлу БД
- DEVICE_INTERVALS - интервалы отправки для каждого типа
- LOAD_TEST - флаг для нагрузочного режима (40 устройств, частые интервалы, очередь на 200)

Проверка переполнения

Чтобы посмотреть, как ведёт себя система при перегрузке, в config.py ставим:

    LOAD_TEST = True
    QUEUE_MAXSIZE = 5

Запускаем - увидим в логах `[QUEUE] Full ... Dropped`, а в статистике счётчик Dropped.
